2.2 THEORETICAL FOUNDATIONS OF REACT COMPONENT TESTING
------------------------------------------------------
A. What is Component Testing?
In React, an application is composed of modular, decoupled components. Component
Testing verifies that a single component renders its expected DOM output, responds
accurately to props, dispatches correct callbacks on user interaction, and manages
its internal or Redux state reliably, without needing a full browser or backend.

B. The React Testing Library (RTL) Philosophy:
Traditional testing frameworks inspected internal component states, private
variables, or implementation details (e.g., shallow rendering in Enzyme).
React Testing Library introduces a user-centric paradigm:
"The more your tests resemble the way your software is used, the more confidence
they can give you."
- Tests do not care if a component is written as a class, function, or custom hook.
- Tests query elements the same way a human or screen reader finds them: by visible
  text (`getByText`), accessible role (`getByRole('button', { name: 'Book Tickets' })`),
  label (`getByLabelText`), or placeholder (`getByPlaceholderText`).

C. The Testing Pyramid:
1. Unit Tests: Test isolated JavaScript functions (e.g., price calculation math,
   sanitization regex).
2. Component / Integration Tests: Render React components in jsdom, simulate user
   clicks and typing, and verify DOM changes and Redux store dispatches.
3. End-to-End (E2E) Tests: Automate real browser sessions (e.g., Cypress/Playwright).
Experiment 1 focuses primarily on Component and Integration Testing.


2.3 TESTING STACK & TOOLCHAIN EXPLAINED
---------------------------------------
1. Jest (v30.5.2):
   - JavaScript testing framework and test runner.
   - Provides test discovery (`*.test.jsx`), test grouping (`describe`), test
     cases (`it` / `test`), assertion library (`expect`), and mocking facilities
     (`jest.fn()`, `jest.spyOn()`, `jest.mock()`).
   - Runs in Node.js and executes tests concurrently with isolated sandboxes.

2. @testing-library/react (v16.3.3):
   - Mounts React component trees into the simulated DOM using `render()`.
   - Exposes the `screen` object for DOM queries.
   - Provides lifecycle cleanup (`cleanup()`) after each test to prevent test leaks.

3. @testing-library/jest-dom (v7.0.1):
   - Extends Jest's `expect` assertions with custom DOM matchers:
     * `toBeInTheDocument()`: Checks whether an element is attached to DOM.
     * `toHaveTextContent(text)`: Checks text inside an element.
     * `toBeDisabled()` / `toBeEnabled()`: Checks input/button interactive state.
     * `toHaveClass(className)`: Checks CSS class presence.
     * `toHaveAttribute(attr, val)`: Checks HTML/ARIA attributes.

4. @testing-library/user-event & fireEvent:
   - `fireEvent`: Dispatches native DOM events (`click`, `change`, `keyDown`).
   - `userEvent`: Simulates higher-level, multi-event user gestures (e.g., hover,
     focus, keypress sequences).

5. babel-jest & Babel Preset:
   - Transpiles modern JSX and ES Module syntax into CommonJS that Node.js
     and Jest can execute seamlessly.

6. jest-environment-jsdom:
   - A pure JavaScript implementation of web standards (HTML DOM, window, document,
     localStorage) running directly in Node.js without launching Chrome or Firefox.


2.4 PROJECT TEST ARCHITECTURE & HELPER UTILITIES (testUtils.jsx)
----------------------------------------------------------------
Because BookMyMovie components rely on Redux Toolkit (`useSelector`, `useDispatch`)
and React Router (`useNavigate`, `<Link>`), rendering a raw `<MovieCard />` would
throw errors (`Could not find store`, `useNavigate must be used within a Router`).

To solve this, we created `src/__tests__/testUtils.jsx`:
```javascript
import React from 'react';
import { render } from '@testing-library/react';
import { Provider } from 'react-redux';
import { configureStore } from '@reduxjs/toolkit';
import { MemoryRouter } from 'react-router-dom';
import bookingReducer from '../store/bookingSlice';
import authReducer from '../store/authSlice';

export function renderWithProviders(
  ui,
  {
    preloadedState = {},
    store = configureStore({
      reducer: { booking: bookingReducer, auth: authReducer },
      preloadedState,
    }),
    route = '/',
    ...renderOptions
  } = {}
) {
  function Wrapper({ children }) {
    return (
      <Provider store={store}>
        <MemoryRouter initialEntries={[route]}>
          {children}
        </MemoryRouter>
      </Provider>
    );
  }
  return { store, ...render(ui, { wrapper: Wrapper, ...renderOptions }) };
}
```
Benefits:
- `preloadedState` allows tests to inject exact scenarios (e.g., 3 pre-selected seats,
  logged-in user session, or empty cart).
- `MemoryRouter` isolates routing history in memory without affecting the real URL.

3.2 WHY OPTIMIZATION MATTERS: THE MONOLITHIC BUNDLE PROBLEM
-----------------------------------------------------------
In a naive React Single-Page Application (SPA):
1. Monolithic Bundle: All routes, pages, components, and third-party libraries
   are bundled into a single huge `index.js` file (often > 1.5 MB).
2. Blank Screen Latency: When a user visits the homepage, the browser cannot
   render anything until it downloads, parses, and executes the entire bundle.
3. Wasted Bandwidth: Users on mobile networks waste bandwidth downloading code
   for pages they may never visit (e.g., admin checkout, terms, food ordering).
4. Main-Thread Stutter: Synchronous image decoding blocks user scrolling at 60 FPS.
5. Zero Resilience: If the internet drops, the app completely crashes.
6. Vulnerabilities: Unsanitized inputs open doors to Cross-Site Scripting (XSS).

Experiment 2 systematically resolves every one of these bottlenecks.


3.3 OBJECTIVE (a): LAZY LOADING MOVIE DETAILS & SEAT SELECTION
--------------------------------------------------------------
What is Lazy Loading?
Lazy loading delays the initialization and network fetching of heavy components
until they are actually requested by the user.

Implementation:
1. Movie Details Page:
   In `src/App.jsx`, instead of a static import:
   ```javascript
   // Static import (unoptimized):
   // import MovieDetailsPage from './pages/MovieDetailsPage';

   // Dynamic lazy import (optimized):
   const MovieDetailsPage = lazy(() => import('./pages/MovieDetailsPage'));
   ```
   The JavaScript bundle for the movie details view is only fetched over the
   wire when the user actually clicks on a movie card.

2. 110-Seat Auditorium Layout:
   In `src/pages/BookingPage.jsx`, the interactive 110-seat grid (`SeatSelection.jsx`)
   contains substantial SVG and tier calculation logic. It is lazy loaded:
   ```javascript
   const SeatSelection = lazy(() => import('../components/SeatSelection'));

   <Suspense fallback={
     <div className="seat-lazy-loading" role="status">
       <span className="spinner"></span>
       <p>Loading 110-Seat Cinema Auditorium...</p>
     </div>
   }>
     <SeatSelection />
   </Suspense>
   ```

Vite Build Verification:
When running `npm run build`, Vite separates these into distinct code chunks:
- `dist/assets/MovieDetailsPage-*.js` (6.09 kB)
- `dist/assets/SeatSelection-*.js` (7.77 kB)
Initial homepage bundle payload is drastically reduced!


3.4 OBJECTIVE (b): ROUTE-LEVEL CODE SPLITTING (React.lazy & Suspense)
---------------------------------------------------------------------
What is Route-Level Code Splitting?
Code splitting partitions the application into independent chunks keyed by URL
routes. Each route is loaded on-demand as the user navigates.

Implementation in `src/App.jsx`:
```javascript
import React, { Suspense, lazy } from 'react';
import { BrowserRouter, Routes, Route } from 'react-router-dom';

// Route chunks loaded on-demand
const HomePage         = lazy(() => import('./pages/HomePage'));
const LoginPage        = lazy(() => import('./pages/LoginPage'));
const RegisterPage     = lazy(() => import('./pages/RegisterPage'));
const MoviesPage       = lazy(() => import('./pages/MoviesPage'));
const MovieDetailsPage = lazy(() => import('./pages/MovieDetailsPage'));
const BookingPage      = lazy(() => import('./pages/BookingPage'));
const SummaryPage      = lazy(() => import('./pages/SummaryPage'));
const FoodOrderingPage = lazy(() => import('./pages/FoodOrderingPage'));
const NotFound         = lazy(() => import('./pages/NotFound'));

function RouteLoadingFallback() {
  return (
    <div className="route-loading-fallback" role="status" aria-live="polite">
      <div className="cinema-spinner" aria-hidden="true"></div>
      <p>Loading Cinema Experience...</p>
    </div>
  );
}

export default function App() {
  return (
    <BrowserRouter>
      <Header />
      <main id="main-content">
        <Suspense fallback={<RouteLoadingFallback />}>
          <Routes>
            <Route path="/" element={<HomePage />} />
            <Route path="/movies" element={<MoviesPage />} />
            <Route path="/movies/:id" element={<MovieDetailsPage />} />
            <Route path="/booking" element={<BookingPage />} />
            <Route path="/summary" element={<SummaryPage />} />
            <Route path="/food" element={<FoodOrderingPage />} />
            <Route path="/login" element={<LoginPage />} />
            <Route path="/register" element={<RegisterPage />} />
            <Route path="*" element={<NotFound />} />
          </Routes>
        </Suspense>
      </main>
      <Footer />
    </BrowserRouter>
  );
}
```
The `<Suspense>` boundary catches the asynchronous loading state during route
transitions and displays an accessible cinema spinner so users never see a white flash.


3.5 OBJECTIVE (c): IMAGE & API DATA RENDERING OPTIMIZATION
----------------------------------------------------------
A. Movie Poster Optimization (`src/components/OptimizedImage.jsx`):
1. Native Browser Lazy Loading:
   `loading="lazy"` instructs the browser to defer fetching poster images until
   they scroll within proximity of the viewport, preserving initial page bandwidth.
2. Asynchronous Decoding:
   `decoding="async"` moves image decompression off the browser's main JavaScript
   execution thread, guaranteeing silky 60 FPS scrolling.
3. Shimmer Skeleton Loading:
   While the image is downloading, a glowing gradient skeleton is displayed:
   ```css
   .image-skeleton {
     background: linear-gradient(90deg, #171920 25%, #252936 50%, #171920 75%);
     background-size: 200% 100%;
     animation: shimmer 1.5s infinite;
   }
   ```
4. Cumulative Layout Shift (CLS) Elimination:
   The poster wrapper specifies a fixed `aspectRatio: '2/3'`. The browser reserves
   exact screen real estate before the image arrives, preventing content jump.
5. Error Resilience:
   If an external poster URL fails (e.g., 404 or ad-blocker), `onError` catches
   the event and displays a styled cinema slate icon (🎬) with title fallback.

B. API Data Rendering Optimization (`src/services/movieApi.js`):
1. In-Memory Caching with TTL (`apiCache`):
   When users alternate between movie searches and detail views, re-fetching
   identical data causes unnecessary network traffic.
   We implemented an in-memory `Map` cache with a 5-minute Time-To-Live:
   ```javascript
   const apiCache = new Map();
   const CACHE_TTL_MS = 5 * 60 * 1000; // 5 minutes

   export async function fetchMovies({ search = '', category = 'all', genre = 'all' } = {}) {
     const cacheKey = `movies_${search.trim().toLowerCase()}_${category}_${genre}`;
     const cached = apiCache.get(cacheKey);

     if (cached && (Date.now() - cached.timestamp < CACHE_TTL_MS)) {
       return cached.data; // Instant return from RAM!
     }

     const freshData = await performNetworkFetch(...);
     apiCache.set(cacheKey, { data: freshData, timestamp: Date.now() });
     return freshData;
   }
   ```
2. Component Memoization (`React.memo`):
   Wrapped `MovieCard` and `SearchBar` with `React.memo` so they only re-render
   when their specific props change, preventing wasteful parent re-renders.

3.8 OBJECTIVE (f): FRONT-END SECURITY PRACTICES & INPUT SANITIZATION
---------------------------------------------------------------------
Front-end security forms the first line of defense against malicious user inputs
and data exposure.

Implemented Security Modules (`src/utils/security.js`):
1. Input Sanitization (Cross-Site Scripting / XSS Prevention):
   `sanitizeInput(text)` strips dangerous HTML and script tags using strict regex:
   ```javascript
   export function sanitizeInput(input) {
     if (typeof input !== 'string') return '';
     return input
       .replace(/<script\b[^<]*(?:(?!<\/script>)<[^<]*)*<\/script>/gi, '')
       .replace(/<[^>]+>/g, '')
       .replace(/javascript:/gi, '')
       .trim();
   }
   ```
   Applied across:
   - `SearchBar.jsx` (movie search query)
   - `Login.jsx` (username/email field)
   - `RegisterPage.jsx` (registration input)
   - `BookingSummary.jsx` (customer instructions)

2. Content Security Policy (CSP) in `index.html`:
   ```html
   <meta http-equiv="Content-Security-Policy" content="
     default-src 'self';
     script-src 'self' 'unsafe-inline' 'unsafe-eval';
     style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
     font-src 'self' https://fonts.gstatic.com data:;
     img-src 'self' data: https: blob:;
     connect-src 'self' https://api.tvmaze.com https://api.themoviedb.org http://localhost:* ws://localhost:*;
   " />
   ```
   Locks down the browser to only load scripts, styles, images, and API connections
   from explicitly trusted origins.

3. Sensitive Financial Data Masking:
   - `maskCardNumber(cardNumber)`: Hides all but the last 4 digits:
     `"4532 1198 3344 4242"` -> `"•••• •••• •••• 4242"`.
   - `maskPhone(phone)`: Masks the middle digits of customer contact numbers:
     `"9876543210"` -> `"987 ••••• 3210"`.
   Prevents shoulder-surfing in public cinemas and log leaks.

4. Input Length & Pattern Enforcement:
   Added strict `maxLength` constraints (e.g., `maxLength={80}` on search inputs,
   `maxLength={60}` on usernames) to prevent buffer and memory exhaustion attacks.

5. VIVA VOCE QUESTIONS & MODEL ANSWERS (30 QUESTIONS)

--------------------------------------------------------------------------------
PART A: COMPONENT TESTING, JEST, RTL & REDUX (Q1 - Q15)
--------------------------------------------------------------------------------

Q1: What is the primary difference between Jest and React Testing Library?
A: Jest is the overall test runner and assertion framework that manages test suites,
runs tests, provides matchers (`toBe`, `toEqual`), and mocks functions (`jest.fn()`).
React Testing Library is a specialized DOM utility that renders React components
into a simulated browser environment and provides user-centric query selectors.

Q2: What is the difference between `getByText`, `queryByText`, and `findByText`?
A:
- `getByText`: Synchronous query. Returns the element if found; throws an immediate
  error if not found (used when the element MUST exist).
- `queryByText`: Synchronous query. Returns the element if found; returns `null`
  if not found (used to assert an element is NOT in the document).
- `findByText`: Asynchronous query. Returns a Promise that waits up to 1000ms for
  the element to appear (used for async API data rendering).

Q3: Why should we use `renderWithProviders()` instead of standard `render()`?
A: Components connected to Redux (`useSelector`, `useDispatch`) or React Router
(`useNavigate`, `<Link>`) crash if rendered in isolation. `renderWithProviders()`
wraps the component in `<Provider store={...}>` and `<MemoryRouter>`, allowing
us to test real component behaviors with custom `preloadedState`.

Q4: What is `preloadedState` in Redux testing?
A: It is an initial state object passed to `configureStore()` to pre-fill the Redux
store before rendering a component, allowing us to test specific scenarios like
pre-selected seats or existing bookings.

Q5: What is `jest.fn()` and how is it used?
A: `jest.fn()` creates a mock (spy) function. It records how many times it was
called, what arguments were passed to it, and what it returned, enabling assertions
like `expect(handleSelect).toHaveBeenCalledWith(mockMovie)`.

Q6: What is `jest.spyOn()` and why is it preferred for API mocking?
A: `jest.spyOn(object, 'methodName')` intercepts calls to an existing method on an
object without altering other methods. In our tests, `jest.spyOn(movieApi, 'getMovieById')`
simulates API responses without making real HTTP network requests.

Q7: What does the `waitFor()` utility do in React Testing Library?
A: `waitFor(() => { expect(...) })` repeatedly runs an assertion callback until it
passes or reaches a timeout (default 1000ms), which is essential when waiting for
asynchronous state updates or API promises to resolve.

Q8: What is `jsdom`?
A: `jsdom` is a pure JavaScript simulation of a web browser's DOM and window APIs
running inside Node.js. It allows React components to mount and dispatch events
without running a heavy headless browser like Chrome.

Q9: What is the purpose of `cleanup()` after tests?
A: `cleanup()` unmounts React component trees that were mounted with `render()`
and cleans up `document.body` to prevent tests from leaking state into each other.
React Testing Library invokes it automatically after each test.

Q10: Why do we test seat removal separately from seat addition?
A: Because seat removal exercises different branches in the reducer: it must locate
the seat ID in the array, remove it without mutating original state, and accurately
decrement the price by that seat tier's price (Regular, Premium, or Recliner).

Q11: How do you assert that a button is disabled in React Testing Library?
A: Using the matcher from `@testing-library/jest-dom`:
`expect(screen.getByRole('button', { name: /confirm/i })).toBeDisabled();`

Q12: How does the deterministic pre-booked seat simulation work?
A: It hashes `movieId + theatreId + date + time` into a pseudo-random seed. This
generates 20–35 consistent booked seats for that exact showtime, ensuring seat
availability remains stable when navigating between views.

Q13: Why is snapshot testing avoided in this project?
A: Snapshot tests are brittle—minor CSS or markup changes cause false failures.
We focus on semantic, behavior-driven assertions (`getByRole`, `toHaveTextContent`)
which verify real user outcomes rather than raw HTML strings.

Q14: How is double-booking prevented in `bookingService.js`?
A: Before persisting a new booking, `confirmNewBooking()` compares requested seats
against existing reservations for the matching showtime. If any requested seat is
already occupied, it throws an error and aborts the transaction.

Q15: What is the format of the generated booking reference ID?
A: It follows the regex pattern `BMM-CBE-[2-9A-Z]{6}` (e.g., `BMM-CBE-9T4K2X`),
providing a unique, collision-resistant reference code for each confirmed ticket.


--------------------------------------------------------------------------------
PART B: PERFORMANCE, CODE SPLITTING, PWA, A11Y & SECURITY (Q16 - Q30)
--------------------------------------------------------------------------------

Q16: What is Code Splitting and why is it beneficial?
A: Code splitting breaks a monolithic JavaScript bundle into smaller, route-based
or component-based chunks. It accelerates initial page loads because users only
download the code required for the current view.

Q17: What does `React.lazy()` do?
A: `React.lazy()` takes a function that calls a dynamic `import()`. It returns a
React component that is automatically loaded asynchronously when rendered.

Q18: Why is `<Suspense>` required when using `React.lazy()`?
A: Because a lazy component loads asynchronously over the network, `<Suspense>` is
required to catch the loading state and display a fallback UI (spinner or skeleton)
until the component chunk finishes downloading.

Q19: What is the difference between `loading="lazy"` and `decoding="async"` on images?
A:
- `loading="lazy"`: Tells the browser to delay downloading the image until it comes
  near the viewport, saving network bandwidth.
- `decoding="async"`: Tells the browser to decode the downloaded image bytes off
  the main JavaScript thread, preventing frame drops during scrolling.

Q20: What is Cumulative Layout Shift (CLS) and how did we prevent it?
A: CLS occurs when images load without defined dimensions, pushing surrounding
content down abruptly. We eliminated CLS by enforcing `aspectRatio: '2/3'` on
poster wrappers so space is reserved before the image arrives.

Q21: How does the in-memory API cache (`apiCache`) work?
A: It stores responses in a JavaScript `Map` using a cache key based on query
parameters (`movies_search_category_genre`). When a request arrives, it checks if
cached data exists and is younger than 5 minutes (`CACHE_TTL_MS`); if so, it returns
the cached data immediately without making an HTTP network request.

Q22: What is a Progressive Web App (PWA)?
A: A PWA is a web application enhanced with a Web App Manifest and Service Worker
that provides native app capabilities: home screen installation, full-screen
standalone display, and offline functionality.

Q23: What are the three core lifecycle events of a Service Worker?
A:
1. `install`: Triggered once when the worker is first registered. Used to pre-cache
   the core app shell assets into the Cache Storage API.
2. `activate`: Triggered when a new service worker version takes over. Used to purge
   obsolete caches from previous versions.
3. `fetch`: Intercepts every network request from the app, allowing custom caching
   strategies (Cache-First, Network-First).

Q24: What is the purpose of `manifest.json`?
A: It provides metadata to the browser indicating how the app should appear when
installed on a device, including app name, icons (192px, 512px), theme color,
background color, and `display: "standalone"`.

Q25: How does the seat selection grid support keyboard navigation?
A: It attaches an `onKeyDown` handler to seat buttons. Arrow keys compute the target
seat index (left/right for seats in a row, up/down for rows A–J) and call `.focus()`
on the target element ID (`#seat-A1`). `Space` and `Enter` toggle selection.

Q26: What is the role of `aria-live="polite"`?
A: It designates a DOM region where text updates are automatically read by screen
readers without interrupting whatever speech the user is currently listening to,
used here to announce seat selection changes.

Q27: What is Cross-Site Scripting (XSS) and how is it prevented?
A: XSS is an attack where malicious JavaScript code is injected through input fields
and executed in other users' browsers. We prevent it via `sanitizeInput()`, which
strips `<script>` tags, HTML tags, and `javascript:` pseudo-protocols using regex.

Q28: What is a Content Security Policy (CSP)?
A: A security standard enforced by browsers that restricts the domains and sources
from which scripts, styles, images, and fonts can be loaded and executed, preventing
unauthorized third-party script injection.

Q29: Why is card and phone number masking important on the front-end?
A: To protect customer privacy against shoulder-surfing in public environments and
prevent sensitive financial data from being exposed in browser logs or analytics.
Only the last 4 digits are visible (`•••• •••• •••• 4242`).

Q30: How many total tests pass across Unit 5?
A: Exactly 70 tests across 9 test suites pass with a 100% success rate:
- Experiment 1: 51 tests across 8 suites
- Experiment 2: 19 tests across 1 suite (plus existing suites re-validated)
- Total: 70 tests passing.
